# 设计说明

这份文档解释 `server.mjs` 里**为什么这么写**。所有部署细节（域名、服务器、端口分配）都在 README 里，本文只用占位符。读完它，你应该能安全地改这个中继，而不是照着抄。

---

## 1. 为什么是「另一个端口上的白名单中继」，而不是「给 GUI 加个密码」

给 DSH 的 web GUI 加一层认证看起来更省事，但它有三个问题：

1. **GUI 是完整的控制面**。认证一旦被绕过（弱口令、cookie 泄露、CSRF、某个没鉴权的静态路由），暴露的是整台机器；而白名单中继即使被完全攻破，攻击面也只有那几条路径。
2. **GUI 会变**。它的路由、静态资源、API 都随 DSH 演进；中继是一层**不随上游漂移**的窄界面（手机端只依赖这个稳定面）。
3. **改不动**。GUI 是 DSH 自己的产物，改它意味着每次升级都要重新打补丁。

代价是中继要不定期跟着手机端的需求扩白名单 —— 这就是下面第 2 节要守的纪律。

## 2. 白名单是硬编码的，这是故意的

`ROUTES` / `STATIC` 两张表在源码里写死，**不提供任何"配置成任意上游路径"的开关**。理由：

- 一个可配置的上游前缀 = 一个任意代理。任何拿到了令牌的人（或任何一次配置手误）就能把 `/api`、把宿主文件系统接口开到公网上。
- 中继只按白名单表决定**发什么 content-type、允许什么方法**，不盲目透传上游响应头。唯一的例外是 `/taskwatch/file`（标了 `passthroughType`）：图片、PDF、文本、视频共用同一条路由，只有上游知道这一份到底是什么类型。

**扩白名单的纪律**：

- 只加**确实需要**的路由；每加一条都要写清「它为什么不是扩大攻击面」。
- 只读的（`GET/HEAD`、不接受输入、不能驱动 agent）风险低，可以放；比如会话用量 `/taskwatch/chat/usage` —— 它只暴露数字。
- 凡是标了 `POST` 的，都等于「把在宿主上驱动 agent 的能力开到了这条路上」，必须显式 `methods: ['POST']` 才放行，并被记录在 README 的安全模型里。
- 默认方法是 `['GET','HEAD']`：漏写就是拒绝，而不是放开。

方法检查放在**路由查找之后**：否则未知路径也会回 405，把「没有这条路由」和「这条路由不吃这个方法」混成同一个现象，排查时白费时间。

## 3. 三条代理分支，各有各的脾气

| 分支 | 关键点 | 不这么做会怎样 |
|---|---|---|
| 普通 JSON（默认） | 读请求体上限 64 KB，`AbortSignal.timeout(15000)` | 没上限 = 让人随便占内存；没超时 = 一个卡住的上游能挂住所有请求 |
| `stream: true`（SSE 对话） | 边收边发、不缓冲、**不吃 15 秒超时**（跟着客户端连接走）、发 `x-accel-buffering: no` | 整段读完再发 = 把流式变成"转圈到最后一起出来"；15 秒超时 = "回复说到一半就没了" |
| `upload: true`（附件） | 请求体**流式**转给上游（`duplex: 'half'`），同样不吃 15 秒超时 | 默认的 `readBody` 是给小 JSON 设计的，一张手机截图就撞上限；攒在内存里再发 = 手机侧"点了上传一直没反应" |

另外，客户端断开时要 `ctl.abort()` 把上游也掐掉 —— 否则一条被放弃的 SSE 会在宿主上一直挂着 follow，每个会话一条。

## 4. 令牌与配对码：两种凭据，两种职责

**令牌**是长期凭据，三种携带方式任一通过即可（`?k=` / cookie / `Bearer`），定长比较（`timingSafeEqual`）避免时间侧信道，转发前从 query 里删掉（绝不带给上游）。

用 `?k=` 首次进入时立刻 302 到去掉 `k` 的地址并种 cookie：令牌不该留在地址栏、浏览历史、Referer 里。只对 `GET/HEAD` 这么做 —— 对 POST 回 302 会让浏览器把请求体重发一遍，语义就变了。

**配对码**解决的是令牌没法解决的问题：手机上要么存书签（误删就完）、要么每次翻 `.token` 文件，而且没有"换一台设备"的正路。

设计上的关键是**「谁能取码」而不是「码有多长」**：

- 取码端点只认 `127.0.0.1` 直连；
- 判断依据**不是 `remoteAddress`** —— 中继前面永远站着一个反向代理，公网请求那条也是 `127.0.0.1`。真正的判据是「有没有经过代理」：看 `X-Forwarded-For` / `X-Real-IP` / `Forwarded`，见到就一律不算本机（**失败即关闭**）。
- 2 分钟、5 次、一次性、同时只有一个码；单来源连续失败 20 次封 10 分钟。这个量级下不能离线爆破。

cookie 是 `HttpOnly` + `SameSite=Lax` + 30 天，并且**每次带 cookie 的请求都重签一次**（滑动续期）。为什么必须滑动：手机搁着不动 30 天就必然掉登录，而"掉登录"在手机端等于"再也进不去"（没人会去翻那台电脑上的令牌文件）。页面每 5 秒轮询一次数据，所以只要打开过一次就一直在续期。

**没有令牌、又是浏览器在导航**（`Accept` 含 `text/html`）时 302 到配对页，而不是甩 401。但 `fetch()` 必须仍然拿到 401：所以判据是 `Accept` 而不是"是不是 GET" —— 否则页面的 `fetch` 会收到 302 + 一段 HTML，`response.json()` 直接抛错。

## 5. 双入口：为什么必须有「换路」这套东西

手机端**不可能**"探测一下再自动选"：

- https 页面不许探测 `http://` 的局域网地址（混合内容被拦，IP 主机连"可升级"都不算）；
- 中继经隧道看到的来源一律是 `127.0.0.1`，也看不出手机在哪个网络。

所以判定只能放在页面里，靠"当前这条路是否失败"来推。中继的职责是**提供事实**和**免输配对码的换路凭据**：

- `/taskwatch/entries` 给出「有哪些入口、你现在从哪条进来」；
- `POST /taskwatch/ticket` 给一张**一次性**通行证，范围被压到最小：18 字节随机值、内存里存着、60 秒过期、兑换即删、只作用于 `/taskwatch` 这一个路径、不做别的。

ticket 的存在意义是：换路不该再让用户去电脑前取一次 6 位码。

## 6. 上游体检与 `x-taskwatch-hop`

"打不开"有三种完全不同的原因（隧道断、上游 DSH 不在、手机缓存了旧响应），而它们在手机上长得**一模一样**。所以：

- 中继自己发的那条 502 **带上 `x-taskwatch-hop: relay`**，并且正文自解释（原因 + 上游地址 + `retry-after: 5`）。没有这个头还是 502，那就不是中继发的 —— 是 nginx/隧道那一段。
- `/taskwatch/upstream-health` 用 4 秒超时探一次上游，把「DSH 正忙/没起」和「网络层坏了」分开。

## 7. 页面外壳与 service worker 本地提供

中继本来就是对外的门面，外壳属于门面的一部分：这样它自包含，不随"上游挂的是哪个插件版本"而变（上游没挂 PWA 路由时也不会漏）。

**一个反例值得记住**：曾经 `public/` 下有一份自己的 `sw.js`，上游插件也有一份，两份行为不同（一份不删旧缓存、也不认 `/taskwatch/session`）。到底拿到哪个取决于请求先命中谁 —— 症状是"有时候更新了、有时候没有"，且完全不可复现。现在启动时只解析一次，两者尽量跟随同一个来源。

读不到页面外壳时退化成**内建兜底页**（`server.mjs` 里的 `BUILTIN_PAGE`），而不是 500：一个缺失的静态文件不该让整条链路变成错误页。兜底页也能自己完成体检、看数据、配对，所以"刚 clone 下来"这个状态是可用的。

## 8. 本地状态只有三个文件，而且都能删

| 文件 | 内容 | 删掉会怎样 |
|---|---|---|
| `.token` | 令牌 | 重启时自动生成新的；所有设备要重新配对 |
| `.lan` | 局域网模式标记 | 回到"只听回环"，隧道那条路不受影响 |
| `.public-url` | 学到的公网入口 | 下次经公网访问时重新学；或改用 `RELAY_PUBLIC_URL` |

用标记文件而不是纯环境变量，是因为中继常由看门狗/服务管理器拉起，那些脚本里改环境变量要动别的东西；放个文件等价，而且"开没开"在目录里一眼可见。两种方式都只是**开关**，不改变鉴权。

## 9. 反面教材：给这一层加 HTTP Basic auth

曾试过在最外面加一层 basic auth，结果是 iOS Safari 发起 service worker 脚本请求（`/taskwatch/sw.js`）时不附凭据 → 那个请求 401 → 新 SW 永远装不上 → 手机一直停在旧页面。服务端一切正常、外部完全查不出异常，是最难排查的一类故障。

正确的做法就是现在的样子：中继自己发一个有时效、可滑动续期的 cookie。
